## 1. Foundational Philosophy

The Litria canvas is a **viewport onto the codebase**. It is not a manager of the codebase.

Files are the source of truth. Always. The canvas reads them, reflects their state, and provides a surface for interaction — but it does not own, control, or arbitrate what the code says.

This principle governs every decision in this document.

---

## 2. The Node

**A node is a file.** One file, one node. Nothing more.

The canvas discovers files and represents each as a node. Nodes are not Litria-invented constructs — they exist because the files exist. If a file is deleted outside Litria, its node disappears. If a file is created, a node appears.

### What a Node Exposes

- File identity: name, path, language
- Defined symbols: functions, classes, constants, variables — everything the file contains, regardless of whether it is currently exported
- Current export surface: what the file is actively exporting (read from the export block)
- Connection anchors: visual points where edges attach

### What a Node Does Not Do

- Does not own import/export logic
- Does not write code autonomously
- Does not gate connections based on static templates

---

## 3. The Edge

**An edge is purely visual.** It represents a relationship that exists in the code. It does not contain logic, does not control code, and is not a source of truth for anything.

The edge is a **discovery and warning layer**.

### One Edge Per Pair

Each unique pair of nodes has exactly one edge. That edge represents the entire import relationship between those two files — it can carry multiple symbols, but it is one line in the consumer's import block and one contribution to the dependency's export block.

A → C is a separate edge from A → B. Even if both carry the same symbol.

### What the Edge Watches (Two-Way Validation)

| Side | What it monitors |
|---|---|
| Dependency (A) | Symbol still defined in A's body |
| Dependency (A) | Export still present at bottom of A |
| Consumer (B) | Import still present and correctly formed |
| Consumer (B) | Imported symbol actually used in B |

Any of these going out of sync triggers a warning state on the edge. The edge is never silently wrong.

### Warning States

- **Broken** — symbol no longer exists in A's body (high severity)
- **Orphaned export** — A's export block exports a symbol A no longer defines (high severity)
- **Unused import** — B imports the symbol but never references it (low severity)
- **Drifted** — symbol renamed, path moved, or manual edit created mismatch (medium severity)

Warning severity may be expressed as distinct visual treatments (color, icon, pulse rate) on the edge.

### What the Edge Does Not Do

- Does not write or remove code
- Does not own connection state
- Does not prevent the user from editing code freely

When a user takes a detach action, that action triggers a code write. The edge disappears because the code no longer supports it — not because the edge removed anything.

## 4. The Drag Interaction

**Drag direction: dependency toward consumer.**

The user drags node A (the file being imported from) onto node B (the file doing the importing). The gesture reads as "give A to B."

### Full Flow

1. User drags A onto B
2. A picker appears, populated with all symbols **defined** in A that are not already on the A→B edge
3. User selects one or more symbols
4. Two code writes occur simultaneously:
   - B receives: `import { X } from './a'` (below the filename header comment, in the import block)
   - A receives: `export { X }` added to the export block at the bottom of the file (if not already present)
5. The edge draws between A and B

### Subsequent Drags on the Same Pair

If A→B already has an edge and the user drags again, the picker opens and shows only symbols not yet on the existing edge. The same edge grows — no new edge is created.

### Auto-Resolve

If A has exactly one defined symbol not yet on this edge, the picker may auto-resolve without requiring user confirmation. This is a UX optimization, not a behavioral change.

---

## 5. The Picker

The picker shows **defined symbols** in A — not just exported ones.

This is intentional. Export is a consequence of the connection being made, not a prerequisite for it. The picker is a definition picker, not an export picker.

### Picker Scope

- All symbols currently defined in A's body
- Filtered to: symbols not already carried by the A→B edge
- This means the picker auto-cleans itself — it only ever shows what hasn't been connected yet

### Picker Excludes

- Symbols already on this edge (already imported)
- Symbols that are broken/undefined (no valid AST entry)

## 6. Export Block Management

Exports generated by the node system live at the **bottom of the dependency file**, in a single managed block.

```js
// bottom of a.js
export { X, Y, Z };
```

This keeps exports aggregated, auditable, and separated from the symbol definitions above.

### Rules

- All node-system-generated exports go in one block at the bottom
- Adding a symbol to a new edge appends to this block (or creates it if absent)
- If A already has an inline `export const X = ...`, that is detected and not duplicated
- The block is a single `export { }` statement that grows and shrinks

### Export Removal Cascade

When a consumer disconnects (Detach + Remove):

- Symbol is removed from B's import statement
- Symbol is removed from A's export block **only if no other edge from A carries that symbol**
- If C also imports X from A, detaching B's edge does not touch A's export block

Export removal never touches the function, class, or const body itself. Only the export statement.

### Symbol Deleted from A's Body

If a symbol is deleted from A's source:

- The edge detects the symbol is no longer defined
- The edge enters a **broken** warning state
- A's export block now has an orphaned entry (exporting something that doesn't exist)
- The user must resolve: restore the definition, swap to a different symbol, or detach

---

## 7. Detach Modes

Right-clicking an edge (or equivalent action) offers two options:

| Mode | Effect |
|---|---|
| **Detach** | Remove the visual edge. Leave the import and export code in place. |
| **Detach + Remove** | Remove the visual edge, remove B's import statement for these symbols, remove symbols from A's export block (only those with no remaining consumers). |

**Detach only** is appropriate when the user wants to clean up the canvas without touching working code. The relationship still exists in the code — the edge will reappear on next project open because the code backs it.

## 8. External Project Support

Because the edge owns nothing and the canvas reads from code, Litria can open any existing project and derive the full node graph.

### Discovery Flow (Existing Projects)

1. User opens a project folder
2. Litria scans files and creates a node per file
3. Litria parses imports and exports across all files
4. Edges draw automatically from what the code already says
5. The resulting graph is the architecture that already exists, made visible

No Litria-specific setup is required. No lock-in.

### litria.project.json

`litria.project.json` is a **generated artifact**, not a gating requirement.

It stores only what cannot be derived from the code:
- Canvas layout (node positions, zoom, pan state)
- User-set groupings or labels

Everything else — file list, import/export relationships, language detection — is read live from the code on every open.

For projects created inside Litria, the file is written at creation. For projects opened from outside Litria, the file is written on first open and is gitignore-able. The manifest does not make the project a Litria project — it is a layout cache.

## 9. SyntaxDomain Role

The **SyntaxDomain** is the analytical engine this system depends on. It is defined in `docs/rfcs/syntax-domain-architecture.md` and its ADRs.

In the context of the node system, SyntaxDomain provides:

| Capability | Used For |
|---|---|
| Parse source files | Discovering defined symbols for the picker |
| Build symbol index | Knowing what A defines, what B imports |
| Detect exports | Reading A's current export surface |
| Reconcile on change | Triggering edge warning state when code diverges |
| Produce patch plans | Generating the import and export code writes |
| Drift/break detection | Driving the edge warning layer |

SyntaxDomain does not know about the canvas. It knows about code. The node system reads from SyntaxDomain and renders what it learns.

### Source of Truth Hierarchy

```
Code files
    ↓ parsed by
SyntaxDomain (symbol index, import/export state)
    ↓ read by
Node System (nodes, edges, warning states)
    ↓ rendered by
Canvas (viewport)
```

The canvas is the top of the display stack and the bottom of the authority stack.

---

## 10. LanguageSupportManager Role

The **LanguageSupportManager** (defined in `docs/plans/language-support-manager-prd.md`) determines which languages SyntaxDomain can parse.

For the node system, this means:

- Edges can only be drawn between files in languages where a pack is installed and active
- The picker can only show symbols if the language parser is available
- A file with no active language support shows as a node but with limited capability (no picker, no export generation, edges flash with a capability warning)

This is the only point where LanguageSupportManager intersects with the node system. It gates capability — it does not control behavior.

## 12. Open Questions

- **Picker UX form factor** — inline dropdown on the canvas, or a modal? Needs to handle multi-select cleanly.
- **Import block ordering** — when multiple edges write imports to B, what order do they appear in? Alphabetical by module path is conventional.
- **Export block conflict detection** — how does the system detect an existing inline `export const X` without parsing errors?
- **Layout persistence for dense graphs** — when App.jsx has 30+ edges, how does the canvas present this without spaghetti? Aggregation and focus/reveal modes are noted in the implementation plan but UX is not yet specified.
- **Picker for re-exports** — if A re-exports from C, are C's symbols available in the A→B picker? Currently out of scope, worth flagging.
